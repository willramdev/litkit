<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party action → CI runner | `changesets/action` executes with the workflow's token; a repointed tag would run attacker code |
| GITHUB_TOKEN → registry + repo | The workflow token can publish packages and push commits/tags — scope it to the minimum |
| ci.yml (read-only) ↔ release.yml (auth-bearing) | The two-workflow split keeps publish auth out of CI |

## STRIDE Threat Register (ASVS L1)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-06 | Tampering | third-party `changesets/action` | high | mitigate | SHA-pin `changesets/action@198f833…` (never a floating `@v2`); a human decision checkpoint (Task 2) confirms the pinned SHA before the workflow first runs |
| T-04-07 | Elevation of Privilege | `GITHUB_TOKEN` scope in release.yml | high | mitigate | permissions scoped to `{contents, pull-requests, packages}: write` only; ci.yml stays `contents: read` and gains no publish auth (two-workflow split) |
| T-04-08 | Information Disclosure | token leakage from CI | high | mitigate | No PAT in CI — release.yml authenticates only via the built-in `GITHUB_TOKEN` (github-token input + NODE_AUTH_TOKEN); nothing to leak beyond the ephemeral job token |
| T-04-09 | Tampering | publish flags | low | accept | publish-script is exactly `npx changeset publish` with no extra flags; no provenance attestation is requested (GitHub Packages internal audience) |
</threat_model>
